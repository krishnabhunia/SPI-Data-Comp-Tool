What breaks and what changes

The published 4.4.0 portable EXE and x64 installer both report NotSigned in Windows. The ZIP matches GitHub's recorded SHA-256. The build workflow never signs the portable application, installed x64 application, installer or uninstaller. PublisherName in the project is display metadata. PR #112 is already merged and only changes navigation. Existing CI passes without checking signatures. No Actions secrets, variables or environments and no local code-signing certificate were found.

Recommended: Implement an optional certificate-store Authenticode pipeline using a real public-trust certificate with a hardware/cloud-backed private key. Keep signing off until its secure runner, provider and protected environment are configured. Require SHA-256 signing, RFC 3161 timestamps and trusted-identity verification before publishing an enabled signing release. Signing establishes the certificate's publisher identity; SmartScreen reputation remains Microsoft's independent decision.

Current download: unknown publisher

Both released EXEs are unsigned. Windows can show Windows protected your PC and Unknown publisher. Existing 4.4.0 files, tags and releases remain historical evidence; this change produces future builds rather than replacing them.

Signing off: explicit unsigned status

With signing unconfigured or explicitly off, ordinary hosted CI and beta builds continue. Logs, the version comment and release notes explicitly say unsigned and that the warning is not fixed. No signing key, provider credential or signing runner is available to PR code.

Trusted release: verified publisher

After configuration, only an eligible protected-master push uses the isolated signing stage. Windows displays the certificate's validated legal publisher name when trust validation succeeds. An unrecognized-app warning may still appear because signatures do not guarantee reputation. This is an intended state, not a claim that a signed build already exists.

Signing enabled but invalid: stop publication

An invalid mode, missing certificate/provider, unexpected signer, untrusted or revoked certificate, failed timestamp, altered binary, missing signature or signing command failure stops publication. There is no silent unsigned fallback. The maintainer repairs the external configuration and reruns normal CI.

Installer and uninstall: complete coverage

Sign the final portable EXE after stamping and Costura weaving, and the x64 application before Inno packing. Use Inno's SignTool callback with SignedUninstaller=yes to cover setup, its temporary self-copies and uninstall. Verify the installed application and uninstaller before the existing smoke checks and uninstall.

External setup required

The owner must acquire a CA-issued public-trust code-signing certificate, complete identity validation, and use a nonexportable hardware/cloud key with a Windows SignTool-compatible provider. Configure a protected windows-code-signing environment restricted to master, an ephemeral Windows signing runner in a restricted runner group, its provider authentication, the expected certificate thumbprint and a provider-approved RFC 3161 timestamp endpoint. Do not upload a PFX/private key. Microsoft Artifact Signing is a potential later backend only after eligibility is confirmed; its public-trust individual enrollment currently supports US/Canada.

What is saved

  • No user database profiles, workbooks, rules, passwords or application preferences change. No application UI/navigation changes are included.
  • Repository configuration stores only a signing mode, runner/environment selection, public certificate thumbprint/store and timestamp URL. Sensitive provider authentication stays in the protected environment or workload identity, with least privilege.
  • The private signing key remains with the hardware/cloud provider. No PFX import, private key file, credential values or replacement root certificates are committed, logged or packaged.
  • CI retains nonsecret signing status, signer metadata, final file hashes, event, head SHA and verification results in logs/release evidence. Keep the distributed ZIP payload compatible with existing strict portable updaters.

What changes elsewhere

  • Implementation affects the existing Windows release workflow, shared signing/verification scripts, optional Inno configuration, focused signing tests, release/version status wording and signing documentation. It does not implement absent macOS or Android code.
  • Secure isolation may require a temporary internal artifact handoff and a narrowly scoped cleanup job with Actions write permission; build/sign jobs retain the minimum permissions needed. The final downloadable artifact remains SPI_Data_Comp_Tool_<version>.zip with platform folders directly inside.
  • Signing contacts the configured provider and timestamp service; Windows verification may contact certificate/revocation infrastructure. Provider costs, certificate acquisition and identity validation are external owner actions.
  • Sign before packaging; never change PE resources, versions or embedded libraries after signing. ZIP hashes authenticate download integrity but do not replace Authenticode.
  • No SmartScreen or Defender settings, execution policies, Mark-of-the-Web data, machine trust stores, merge settings, existing tags or releases are changed. No manual publishing workflow is triggered.

Alternatives

Optional certificate-store pipeline — Recommended

Fits the existing Win32/SignTool/Inno packages and supports a CA/provider appropriate to the validated signer. A hardware/cloud-backed provider can keep the key nonexportable. The owner must provision and restrict its CI runner before enablement.

Microsoft Artifact Signing with OIDC — Not recommended

A strong managed option for eligible identities, but eligibility and an Azure signing account/profile are not established here. Individual public-trust enrollment is currently limited to US/Canada. This revision documents it as an alternative, without pretending credentials exist or adding an unconfigured second backend.

Microsoft Store MSIX distribution — Not recommended

A legitimate alternative with a different packaging/submission/update model. It would require a separate distribution project and does not repair the existing GitHub portable and Inno EXEs within this request.
